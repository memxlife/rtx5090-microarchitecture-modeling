# RTX 5090 parameter table

The research goal is to determine whether realistic RTX 5090 kernel optimization can be formulated as a mixed-integer program and solved efficiently. Provisional values are useful when they reasonably reproduce hardware measurements; precise identification of every private circuit is not the acceptance criterion. The current target is roughly 5% runtime error on separate workloads, together with useful optimization choices and measured solver time.

The one-hour evidence pass is recorded in the [consolidated checks](parameter_sweep/initial_validation_20261003_222837/consolidated_checks.md). That table separates supporting observations, model-only checks, implementation mismatches, and entries still lacking support. New [effective timing costs](initial_validation_effective_profile.json) replace complete tested paths rather than adding another delay.

This single table contains **151 rows**: the original 134 discovery entries plus 17 recorded capacities, limits and operating-point values. The total is calculated from the entries, rather than held to an earlier target. K-prefixed rows consolidate values from the quantitative specification and current model configuration; F/T-prefixed rows retain the discovery inventory. A row may be a family of values, so this total is not a count of independent scalar constants. The [completeness audit](parameter_completeness_audit.json) and [quantitative specification](quantitative_microarchitecture.md) retain source and scope details. Further omissions and overlaps remain under review.

Here an SM is a streaming multiprocessor, a compute block that runs warps. A warp is a group of threads executing together; a lane is one thread position. L1 and L2 are successive data-cache levels. A cache set is an indexed group of lines, a way is one line position in a set, and a sector is a separately tracked piece of a line. A bank is a storage subdivision that can serve accesses independently. A queue holds unfinished work; arbitration chooses which waiting operation proceeds. An instruction issues when it is accepted for execution.

**Evidence status:** Identified means established for the recorded scope; Partial means some cases or combined behavior are supported; Unknown means the named physical property has not been identified. Every entry has a provisional baseline, but a baseline does not turn an unknown property into a verified fact.

**Difficulty:** Easy means a source/query check or a repeat of an already demonstrated scoped probe. Medium means a controlled sweep over addresses, instructions, numerical cases or concurrency. Hard means distinguishing hidden structures or interacting mechanisms that several different explanations can reproduce. These are first-pass planning estimates, not promised completion times. An easy effective timing measurement still does not identify the separate internal delays that contribute to it.

Within the original 134-entry discovery inventory, the reviewed classification has **26 Easy, 38 Medium and 70 Hard entries**. The 17 additional recorded-property rows are Easy to check and are included in the same table. Overall difficulty is 43 Easy, 38 Medium and 70 Hard. Some recorded values are model settings or conversion choices, explicitly labeled; they are not identified physical facts. The Easy group contains eight already identified entries and 18 incompletely identified entries. The initial 34-candidate list was narrowed after eight entries were judged to need controlled sweeps. Evidence totals remain **8 identified, 32 partial and 94 unknown**; these earlier physical-identification classifications are retained separately from the new initial evidence checks.

A cycle is one tick of the stated reference clock. A nanosecond is a unit of elapsed time. A service rate counts operations or bytes per unit time; it is different from the delay before one operation returns a result. Values below are reproduced from the [current provisional profile](provisional_hardware_profile.json), including its scope limits. Source-backed or measured values support only their recorded subcase; assumed values are simulation choices.
