# Does the cost of staging operands explain GEMM timing?

The matrix-loop experiment found a throughput ceiling but no substantial benefit from independent accumulator chains. Complete GEMM profiles showed considerable waiting for memory operands. We now ask whether the cost of moving operands from global memory into shared memory behaves independently of computation, or changes when the two appear in one loop.

The diagnostic uses the existing BF16-to-FP32 matrix primitive, four warps per block, reduction tiles of length 32, and output tiles of 32 by 32 or 64 by 48. Four versions run the same loop and barriers: a control, staging only, computation only, and staging plus computation. All versions read and sum the shared tile on every iteration. This extra checksum keeps staging observable and is identical across the four versions. The computation consumes every accumulator element. Each output is checked against the exact result for constant inputs.

We subtract the control cost when comparing isolated staging and isolated computation with the combined loop. If the combined incremental cost differs consistently from the sum of the isolated incremental costs, the additive phase model is insufficient in this diagnostic. A smaller combined cost is consistent with overlap or different scheduling; a larger cost is consistent with contention or changed capacity. Neither observation alone uniquely identifies its cause. Different compiled register requirements remain a possible confound and are recorded. This factorial comparison is more informative than refitting full-GEMM coefficients because it measures the phase interaction directly.

We use one block, 170 blocks, and 1020 blocks, with reduction lengths 768 and 2304. A separate shared-memory reservation of 49,152 bytes limits block residency across all variants, helping distinguish phase interaction from residency changes. We record actual resident-block limits rather than assuming the reservation matches all resources. The main tile and reduction sweeps are development evidence; the second tile is a transfer check, not untouched confirmation of a model trained on these data.

A staging control groups four global loads before their shared-memory stores. It preserves requested bytes and outputs, but may change instruction scheduling, loop overhead, register requirements, and resource capacity. It therefore tests whether a generated load schedule helps, rather than measuring a pure outstanding-request parameter. We inspect compiled instructions before assigning a mechanism. A second control adds a barrier between the checksum and computation while preserving both necessary producer-consumer barriers. This safely measures sensitivity to an additional synchronization point; it does not justify deleting required barriers.

Inputs are constant and global addresses follow the same row-major staging pattern, but this diagnostic has simpler block mapping and no boundary predicates. Blocks share the B input. Hardware caches remain active, and explicit L2 modeling is excluded. Results apply to this controlled access pattern; full-GEMM timing and correctness must confirm any optimization before adoption. The checksums also add shared-memory work absent from the production kernel, so these measurements cannot be substituted directly for production phase costs.

All measurements run on GPU 7 after an idle check. We retain five repeats, cycle counts, elapsed time, register use, spills, residency, source, compiled instructions, and clock, temperature, and power snapshots. No clock or power setting is changed. Snapshot telemetry does not establish constant operating conditions during every kernel. The MILP model remains frozen.

## Full-GEMM transfer check

The phase results justified a separate test of grouped loads in the actual GEMM. We compile one-load and four-load versions from the same source, preserving boundary handling, tile shape, shared layout, matrix work, and both necessary barriers. Ordinary C++ loads are used here, as in the original GEMM; the diagnostic's explicit load instructions are not transplanted. Two workloads, 1728 by 2112 by 2304 and 960 by 1152 by 640, are each tested with both tiles. Two paired repetitions reverse the order of the load schedules. Each execution checks every output against cuBLAS and reports nine timing samples, with the existing cache sweep before each launch. Registers, spills, and residency accompany the timings. This tests transfer of the schedule effect without fitting the MILP model. Since the diagnostic already used the larger reduction length, these workloads are implementation confirmation rather than an untouched prediction test.

The real-GEMM transfer check found slowdowns rather than improvements. We therefore repeat the larger workload with a 49,152-byte shared-memory reservation for both schedules, again reversing order across two paired repetitions. The queried resident-block limit is one for all four full-GEMM variants: their additional static shared memory makes this reservation more restrictive than the phase probe. This tests whether the slowdown survives removal of the residency difference. Four profiles measure instruction counts, memory-request sectors, and operand-wait counters under that reservation. Their purpose is to distinguish the observed schedule effect from the occupancy explanation, not to make profiler elapsed times the timing authority.
