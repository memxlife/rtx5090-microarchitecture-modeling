# The dense regression has a provable producer issue bottleneck

Why does the staging repair improve the small matrix but slow a previously accurate large case? The repaired producer executes 868 warp instructions per block and reduction stage, yet its scheduler accepts only one instruction per streaming multiprocessor (SM) per cycle. An SM is one GPU compute cluster. This limit gives a useful bound without another simulation or fitted latency.

For 1,920×1,920 output elements, 32×32 tiles require 3,600 blocks. Distributed over 170 SMs, at least one SM executes 22 blocks. Each block has 48 reduction stages. Therefore that SM must execute at least `22 × 48 × 868 = 916,608` producer issue events. The candidate cannot finish faster than 916,608 cycles under its own one-issue rule, even with zero memory delay. Its actual result is 945,861 cycles, only 3.19% above that bound. The old result was 720,853 cycles. Reducing the 340-cycle readiness prior or enlarging queues alone cannot recover the old result while keeping the same instruction count and issue rule.

The small case has only twelve blocks, so each active SM handles one block and 384 stages. Its producer issue bound is 333,312 cycles, far below the candidate's 994,607 cycles. Dependency waiting and sequential staging/compute phases therefore matter much more there. The existing component check needs 2,013 cycles for a complete producer stage with early memory returns, despite only 868 issue events. That is model behavior, not a measured hardware stage latency.

The repair does not add 340 cycles to cache latency. It releases each load at the later of its issue-plus-340 deadline and its final returned sector plus one cycle. However, the 32-entry global-load queue retains its entries until that deadline, even if sectors have already returned. With 64 loads per stage, this queue alone implies at least `64 × 340 / 32 = 680` cycles per stage on average under continuous occupancy. For the dense case that is 718,080 cycles, still below the stronger 916,608-cycle instruction bound. It is a separate pool from the configurable 32 native shared-read slots; the identical number does not establish that these represent the same physical hardware.

Different blocks can stage and compute concurrently. The controller waits for staging before computing within one block, but the SM advances producer and native engines separately each cycle. Thus the candidate can issue one producer and one native instruction simultaneously for different contexts; it has neither one unified issue owner nor four modeled hardware scheduler partitions. Native shared reads and staging writes still interact through the shared-memory interface. This is a mixed resource abstraction, rather than an exact instruction scheduler.

Saved device attributes report four schedulers per SM, one maximum instruction per scheduler per cycle, and four maximum instructions per SM per cycle in three profiles. They do not reveal warp assignment or which instructions can attain that peak. The next structural correction should represent those scheduler ownership constraints explicitly and validate their effect; simply assigning four issue slots would remain a hypothesis. The current evidence proves that the candidate's one-producer-issue limit forces its dense slowdown. It does not prove that this explains every physical timing discrepancy.
