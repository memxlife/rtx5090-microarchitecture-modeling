# Does instruction dependency explain a missing GEMM timing cost?

Our current model counts matrix work and estimates whole-GPU capacity. It does not explicitly represent the wait between dependent matrix instructions. We test whether independent accumulator chains reduce the time required for the same number of matrix operations on one RTX 5090. This is a diagnostic experiment; the existing performance model remains frozen.

Each warp uses the same BF16 inputs and FP32 accumulation through the same 16-by-16-by-16 CUDA matrix primitive as the GEMM kernel. We vary the number of independent accumulator chains from one to two, four, and eight. A warp always performs 16,384 matrix operations. A second, shorter measurement uses 4,096 operations to check whether startup costs materially affect the result. Each loop iteration contains eight matrix operations in every variant, so loop overhead is matched. All accumulator elements are consumed to prevent the compiler from discarding unused output columns. Every output is checked against its exact expected value. Compiled instructions and register usage are preserved; a spill or a change in the matrix instruction shape prevents a clean dependency comparison.

We first use one block with one warp. If extra independent chains reduce cycles per operation by more than the repeat variation, this supports dependency-limited execution. If they do not, dependency latency may already be close to the issue interval, or another resource may dominate. Either result narrows the explanation without establishing a GEMM-level cause. This test is cheaper and easier to interpret than fitting additional coefficients to complete GEMM timings.

Next we vary one, four, and eight warps per block, with one block or 170 blocks. The fixed-work comparison uses one block; the 170-block cases measure scaling with explicitly larger total work. We report cycles per warp operation and aggregate elapsed time separately. We do not interpret increased total throughput as reduced latency for a fixed problem. Register usage and resident-block limits accompany every measurement because extra chains can change resource capacity.

We record GPU clocks, temperature, power, and memory use before and after each case. We do not change clocks or power limits. These snapshots bound measurement conditions but cannot reconstruct every clock transition during a short kernel. Explicit L2 modeling remains excluded; hardware caches remain active. The matrix loop uses operands already loaded into registers, so its result does not depend on repeated global-memory loads.

Finally we profile the two existing GEMM tiles on the same workload to compare dependency stalls, barrier stalls, memory stalls, eligible warps, and issue activity. These counters identify where to investigate next; they cannot uniquely distinguish a register-port bottleneck from other scheduling limits. An isolated memory-transfer experiment is deferred until these measurements indicate which part of the actual transfer path needs a matched control.

The run is limited to GPU 7, only after checking that it has no active compute process. We preserve source, compiled instruction listings, raw repeats, telemetry, profiler outputs, and a concise interpretation in this directory. These data will not be used to refit the model during this diagnostic round.
